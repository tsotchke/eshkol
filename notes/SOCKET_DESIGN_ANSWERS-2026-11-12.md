# Socket design answers and review decisions

The [November 13 review followup](../docs/development/evidence/unix-socket-review-followup-2026-11-13.md) records the updated branches, review corrections and source-bound test results.

Draft answers to the [design questions](https://github.com/tsotchke/eshkol/pull/922#issuecomment-6833436073) and [review](https://github.com/tsotchke/eshkol/pull/922#pullrequestreview-5880625342). Socket decisions below describe this slice; shared API migrations and future work are proposals for coordination.

## A. Socket decisions

1. **Capabilities:** keep `network` for this v1.4 socket slice, checked at both Scheme and native admission/I/O. This preserves the agreed policy and avoids adding a new permission implicitly. A future `local-ipc` capability is useful for allowing local IPC without Internet access, but needs an explicit policy migration. The current capability API is a symbol allow-list, not a path grant system; passing a path as error context does not enforce a path restriction. If path grants are introduced, binding needs permission to create that endpoint and connecting needs permission to connect to that endpoint, in addition to the socket capability. Generic `file-read` is not a substitute for connection permission. Private 0700 parent validation and 0600 socket mode remain required. Owned cancellation/cleanup do not reacquire policy.

2. **Typestate:** listener acquisition returns an owned listener. `connect-begin` conservatively returns an owned connecting stream, even if the native connect already succeeded; successful `connect-finish!` transitions it to open without consuming ownership. Read/write borrow open streams. Cancel borrows and transitions the owner to cancelled; cancellation never closes it. Poll may observe cancelled state. `close!` consumes the socket; `close-request!` consumes it and returns an independently owned cleanup ticket. Close acceptance retires the I/O identity; torn down is an outcome of cleanup, not another usable socket state. Every module export has a reviewed row. Compound PROCESS cleanup IDs remain explicitly unsupported in strict mode until aggregate ownership is modeled; that limitation is not presented as a safe operation.

3. **Tickets:** the ticket is a checked owned handle; its result vector is plain snapshot data. Observation does not consume a ticket. Release consumes a terminal ticket; retryable failures remain owned. Pending/retryable teardown retains the loop. Once teardown is terminal, the loop retain ends even if its result ticket has not yet been released, so terminal result ownership does not prevent loop shutdown. Revocation does not disable result inspection, retry or release. This does not make a foreign observer an I/O owner.

   **Retry's checker role is deliberately OBSERVE.** It borrows the same owned ticket, without consuming it, producing another owner or changing its handle kind. An ownership observation may perform I/O; it is not a purity annotation. Failed/pending/terminal are runtime snapshot states, and retry does not prove completion, so the caller inspects again before release. Cancel uses TRANSITION because it changes the socket's protocol kind and therefore which I/O operations are admissible. Modeling cleanup-result refinements would be a separate checker feature; a transition row alone would not provide that proof.

4. **Scopes:** recognize `call-with-unix-stream-listener`, `call-with-unix-stream-connection` and `call-with-unix-stream-accept` as synchronous loans. The listener may stay borrowed by an outer listener scope while a loop repeatedly uses scoped accept. Each peer accepts close on return, exception or continuation escape; the borrowed handle cannot be closed, returned or captured for later use. Re-entry is refused. Scoped finalization owns its internal ticket, makes one bounded cleanup retry, and releases a terminal result. A normal return reports cleanup failure with plain context/identity/snapshot data. Exception and continuation exits preserve their original control; callers needing guaranteed cleanup-error inspection on those exits use manual ticket forms. A genuinely pending/watch failure stays detached and retained for safe recovery, never falsely freed. Manual ownership also remains available when a peer must outlive one callback.

5. **Platforms:** native hosted Linux/macOS are the intended implementation targets, with separate qualification. Bytecode VM, Windows and WASM explicitly refuse this socket bridge until they have ownership/readiness adapters; tests must establish refusal rather than infer support from AF_UNIX availability. Remove the Windows family probe from the addendum: a positive family probe would not make this API usable. Hosted native Linux/macOS execution is now recorded separately. macOS public JIT/AOT and package qualification remain open. Abstract namespace names are invalid and have an acceptance control.

## B. Shared-layer proposals

6. **TCP/UDP/TLS:** the ownership principles apply broadly: no new uses after accepted close, no repeated descriptor close, safe lifetime after cancellation. Explicit loop parameters and sticky cancellation are API behavior changes, so do not silently retrofit them into the existing net/TLS surface in this socket PR. The common adoption/wait facility supports those policies. A coordinated migration would change acquisition in `net.c`/`tls.c`, add explicit loop forms in their headers/wrappers, select sticky cancellation at adoption, and move native/TLS teardown into owner callbacks with matching tests/contract rows. TCP half-close and TLS protocol shutdown remain distinct operations; PROCESS additionally retains budgeted termination/reap semantics. The existing legacy net/TLS behavior is preserved and tested here.

7. **Ticket sharing:** share the engine in `resource_lease.h`; expose the new ticket surface publicly for Unix sockets first. The minimal mechanism is loop-aware adoption with a teardown callback, accepted-close returning a reserved ticket, coherent result inspection, explicit retry and terminal release. Other families can adopt it deliberately. PROCESS keeps its checked session/reap protocol until a public adapter and aggregate ownership contracts are designed; a generic resource close must not retire a live PROCESS cleanup owner.

8. **ABI:** keep published handle-kind values stable: FILE/SOCKET/EVENT_LOOP = 1/2/3, WINDOW/AUDIO_DEVICE/MIDI_PORT = 4/5/6, PROCESS/CLEANUP = 7/8. Public struct layouts and function signatures require normal ABI discipline. Tokens are opaque, generation-checked, runtime-local identities; their incidental slot/generation bit pattern is not a serialization format. Moving loop identities to the shared registry is documented. Private managed flags/index metadata do not change the public token layout.

9. **Landing shape:** separate the four integration repairs, common lease/loop foundation and socket core. Keep #914's PROCESS ownership contracts with #914. Land the repairs and the independent shared foundation first; #914 can then use that foundation for its PROCESS adapter and ownership contracts. Advance #916 to the amended scaffold, then land the socket core. This puts the common registry dependency before its PROCESS adapter; #914 still precedes the socket scaffold/core. Dependent PRs must identify their prerequisites and provide comparisons that exclude them; retarget/rebase against the canonical integration branch once prerequisite merges are available. Do not carry unrelated generated backend API pages or raw machine logs through this stack.

## Cleanup-ticket questions

- **Terminality belongs to the callback.** The shared layer never invents a timeout or declares an unresolved callback complete. For Unix pathname cleanup, the initial failure is retryable; one explicit repair/retry is allowed (scoped finalization performs that bounded retry internally). A second failed attempt is terminal and records PATH plus its OS error, releasing native bookkeeping and the loop retain while leaving the residual pathname for the caller to repair manually. Successful retry removes only the originally recorded inode. An uncertain descriptor close is never retried.
- **Loop close:** pending or retryable cleanup blocks loop destruction. Terminal result tickets do not. Owner-thread result inspection/pumping resolves pending work; BUSY is the documented refusal while retention remains. A diagnostic that identifies outstanding cleanup owners is useful future work; no such diagnostic is claimed here.
- **Keep one reserved ticket per resource.** Serial callbacks can still leave several failures unresolved at the same time: cleanup A fails, cleanup B fails, both results remain owned. A single per-loop “most recent failure” would overwrite responsibility or require a second allocation/queue during close. Pre-reserving each resource's result permits allocation-free accepted close and independent observation/release.
- **Foreign observation:** keep queries observational. Close/cancel already signal the owner loop; another query cannot force a thread that has stopped servicing its loop to run teardown. Document the required owner progress rather than imply that repeated notifications guarantee completion.
- **Retry after revocation:** allow it. Retry only discharges an existing cleanup obligation for the exact recorded entry this process created; it cannot acquire a new path or replace an entry. It cannot unlink a replacement inode. The pathname failure result remains visible if cleanup becomes terminal.
- **Keep both close verbs:** `close!` is the detached convenience; scoped helpers privately own and finish a ticket through the same engine. Successful results are released automatically and the strict profile permits one recovery claim for a failed result through the retired identity. `close-request!` explicitly transfers an owned ticket to the caller. Making `close!` always return a linear ticket while also saying it may be ignored gives the ownership checker two conflicting rules. The retired token is recovery authority only, never renewed socket authority.

## C. Work beyond this slice

10. **SSE:** deferred from this socket revision; no SSE implementation or ownership assignment is included in this response.
11. **HTTP/WebSocket validation:** propose dedicated lanes implement those independent protocol-validation changes, with me reviewing the resource/cleanup integration. This is a coordination proposal, not a claim that those lanes have started or a commitment to own all protocol work in the weeks of November 16/23.
12. **macOS:** keep socket/net/TLS/subprocess macOS qualification as a required platform gate. I propose running the agreed matrix on an available macOS host or hosted runner. The new hosted arm64 run establishes native socket/common/PROCESS acceptance only; net/TLS, public JIT/AOT and packaging remain separate. I am not claiming a standing weekly host is available.
