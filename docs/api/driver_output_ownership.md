# `eshkol/driver_output_ownership.h`

Who owns a native output path, and the files beside it, while the driver compiles and links. Three kinds of file appear beside `<output>` during a native build, and each has exactly one owner: - `<output>.eshkol-link.lock` is the claim on the output path. One driver holds it from before it compiles until it has published or given up. The hold is an operating-system file lock, so it ends with the process on every exit path, including one the process cannot observe; a claim file left behind by a process that is gone is simply taken over by the next compile of that output, which is also the only thing that removes it: the file names no process, and only a claimant can tell a leftover from a live claim. A second driver that asks for the same output while the first is alive waits for it, for a bounded time, and is then told the output is owned. Where the filesystem has no file locks, the build goes on without a claim (staging still applies). Where the output is not a regular file (a device such as `/dev/null`), there is no claim and no staging: the build proceeds in place. - `<output>.<pid>.<n>.tmp.o` is the scratch object the driver compiles before the link. - `<output>.link-<pid>-<n>.d/` is the staging directory the linker writes into. The finished artifact carries its final leaf name there and is moved onto `<output>` in one rename, so a reader of `<output>` sees the previous artifact or the new one, never part of either. The last two carry the process id of the driver that made them. A driver that is stopped before it can clean up leaves them behind; the next driver for the same output removes those whose process no longer exists. A process that is alive, or whose state cannot be determined, keeps its files. Staging is the caller's choice per build. The driver links in place, still under the claim, where a debug companion is named from the link path: every Windows debug build, and on any platform a debug build of a program with no objects to link. Publication is a rename onto the output name. An output name that is a symbolic link is therefore replaced by the artifact; the file the link pointed at is left as it was. Header-only and free of compiler dependencies so the naming and liveness rules can be exercised on their own on every platform. The Windows branches below were written against the documented behaviour of the Win32 calls they use; the Windows lanes of CI are their first build and their first run, through driver_output_ownership_test.

### `OutputClaim`

*class* — line 280

```c
class OutputClaim
```

The claim one driver holds on an output path. Not copyable. Releasing (or leaving scope) removes the claim file and ends the hold. If the process ends without releasing, the operating system ends the hold and the next claimant takes the file over.

### `OutputClaim::lock_error_means_unsupported`

*Function* — line 299

static bool lock_error_means_unsupported(int error) { ... }

Whether a failed lock request means "this filesystem has no locks" rather than "the lock is taken" or "something is wrong". Network and user-space filesystems answer a lock request with one of these.
