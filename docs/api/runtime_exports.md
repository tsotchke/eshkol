
Installs a policy from a whole set of names, in one call. The way a program installs a policy, and a single call on purpose: a policy is never active with its set still being assembled, so there is no window in which a stray grant could widen it. **Returns**

### `eshkol_capability_runtime_begin_install`

*Function* — line 302

```c
void eshkol_capability_runtime_begin_install();
```

Opens a staged install, for a host embedding Eshkol. For an embedder that builds its allow-list as it goes: begin, then one eshkol_capability_runtime_allow() per name, then eshkol_capability_runtime_end_install(). A program's own code never reaches it — it installs through eshkol_capability_runtime_install(), and the staged entry points are refused in an `(extern ...)` declaration and absent from the bytecode VM's table. While the install is open the policy is active with nothing granted, so a concurrent check fails closed. On an already-active policy the current set becomes the ceiling the staged names are intersected with.

> Note: Thread-safe.

### `eshkol_capability_enforce`

*Function* — line 426

```c
void eshkol_capability_enforce(const char* capability, const char* operation);
```

The gate at a capability sink: permit the operation, or raise a catchable Eshkol error naming the capability. This is the enforcing counterpart to eshkol_capability_require(), for sinks whose only correct answer to a denial is a raise rather than a sentinel return value — process creation, shell execution, socket creation and dynamic library loading all fall in that class, since every return value they could produce is also a legitimate one. With no policy installed this returns immediately and the program behaves exactly as it did before capabilities existed. Under an active policy that does not grant `capability` it raises ESHKOL_EXCEPTION_ERROR with the message "capability denied: <capability> (<operation>)", which `guard` catches like any other error; an unhandled raise ends the program the same way an unhandled `(error ...)` does, rather than continuing into the sink.

**Parameters**

- `capability` — Capability name the sink requires, e.g. "subprocess". NULL requires nothing and returns.
- `operation` — The operation to name in the message, e.g. "process-spawn". NULL is reported as the capability name alone.
