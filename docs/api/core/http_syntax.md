### `eshkol_http_valid_received_header_line_n`

*Function* — line 409

```c
static inline int eshkol_http_valid_received_header_line_n(const char* text,
 size_t length) { ... }
```

A received field line: the sending grammar, plus HTAB in the value. Eshkol refuses HTAB in a value it *sends*, because a proxy on the path may re-split a value on it. RFC 9110 section 5.5 nonetheless admits HTAB in a field value, and real `Cookie` and `User-Agent` strings carry it, so a server that refused one would reject conforming traffic. Receiving is therefore held to the RFC's set and sending to the stricter one; every other control byte, CR, LF, NUL and DEL included, is refused on both.

**Parameters**

- `text` — Field line, not NUL-terminated.
- `length` — Length of `text` in bytes.

**Returns**

1 when the line is one a peer may legitimately have sent.

### `eshkol_http_reserved_field_name`

*Function* — line 481

```c
static inline int eshkol_http_reserved_field_name(const char* name,
 size_t length,
 int websocket) { ... }
```

True when `length` bytes at `name` name a field an Eshkol client writes itself, so a caller may not also supply it. Two kinds of field are reserved. The framing and connection-control fields (`Content-Length`, `Transfer-Encoding`, `Host`, `Connection`, `Upgrade`) are emitted by every client from the request it was given; a caller-supplied second copy puts two framing headers on the wire, and RFC 9112 section 6.3 forbids a sender emitting both a `Content-Length` and a `Transfer-Encoding`. A front end honouring one and a back end honouring the other desynchronise, which is request smuggling. The handshake fields (`Sec-WebSocket-Key`, `-Version`, `-Accept`, `-Extensions`, `-Protocol`) are derived per connection from the CSPRNG and must not be forced by a caller.

**Parameters**

- `name` — Field name, not NUL-terminated.
- `length` — Length of `name` in bytes.
- `websocket` — Non-zero to reserve the `Sec-WebSocket-*` set as well.

**Returns**

1 when the name is reserved, 0 otherwise.
